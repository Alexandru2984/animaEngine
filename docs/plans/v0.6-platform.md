# v0.6 — Platform completeness (Faza T)

Detailed execution plan. Umbrella: [docs/roadmap-1.0.md](../roadmap-1.0.md).
One sub-phase = one commit, standard gate before each
(`cargo fmt --all` + clippy `-D warnings` + `cargo test --lib`).

Theme: the engine behaves identically everywhere it claims to run.
Two long-standing gaps close: global shortcuts on GNOME/KDE Wayland
sessions (portal), and the multi-monitor data model from 0.3 finally
getting a render-side implementation.

## Current state (what we build on)

- Hotkeys: `src/hotkeys.rs` registers 3 chords via the `global-hotkey`
  crate (XGrabKey). Works on X11/XWayland; silently unavailable on
  native Wayland, where `docs/wayland.md` documents compositor
  bindings calling our D-Bus methods.
- Multi-monitor: `src/monitor.rs` has `MonitorInfo`,
  `resolve_monitor_for_position`, per-entity `monitor` pin and
  `MonitorMode` (PerMonitor / Span / Single) — all consumed only for
  entity *positioning math* today; rendering is one window.
- D-Bus: zbus 5 in tree, session connection held by single-instance.
- Pacing: `RedrawPacing` per window assumption baked into
  `App::redraw_pacing` — multi-window must generalise it.

## T.0 — Portal probe + strategy log (S)

**Goal:** know at startup which hotkey strategy this session supports;
log it; change nothing else.

- New `src/hotkeys/` module dir (move existing `hotkeys.rs` →
  `src/hotkeys/mod.rs`, sctk-style).
- `src/hotkeys/probe.rs`: query
  `/org/freedesktop/portal/desktop`,
  `org.freedesktop.portal.GlobalShortcuts` property `version` via
  `org.freedesktop.DBus.Properties.Get`. Reuse a fresh session
  connection (cheap, one call at startup).
- `pub enum HotkeyStrategy { Portal { version: u32 }, X11Grab, DbusOnly }`
  + pure `fn choose(portal: Option<u32>, is_x11: bool) -> HotkeyStrategy`.
- `main.rs`: log the decision next to the existing hotkey
  registration; keep registering XGrabKey exactly as today.

**Tests:** `choose()` truth table (portal beats x11; x11 when no
portal; DbusOnly when neither). Probe itself is integration-only —
skipped without a session bus.

**Acceptance:** startup log shows `Hotkey strategy: Portal{v2}` on
GNOME Wayland, `X11Grab` on bare X11, `DbusOnly` on wlroots without
portal. Zero behavior change.

## T.1 — Portal client module (M)

**Goal:** a self-contained client for the GlobalShortcuts portal.

- `src/hotkeys/portal.rs`:
  - `CreateSession` with `handle_token` + `session_handle_token`;
    response via `org.freedesktop.portal.Request::Response` signal
    (the portal request dance — token, path, subscribe-before-call).
  - `BindShortcuts(session, [(id, {description, preferred_trigger})], parent_window)`
    — ids are our `Action` slugs (`toggle-edit-mode`, `hide-overlay`,
    `pause-all`); preferred triggers from the user's `KeyBindings`.
  - Subscribe `Activated` / `Deactivated` / `ShortcutsChanged`.
  - Persistence: the portal remembers bindings **per app-id** (no
    restore token in this portal — that's a ScreenCast concept;
    corrected during T.1), so re-binding on later launches doesn't
    re-prompt. Nothing portal-related lands in config.toml.
- Events flow through a **bounded** `sync_channel(64)` (same pattern
  + rationale as `single_instance.rs`); a dedicated thread owns the
  zbus connection (same lifecycle as `install_service`).
- All portal calls best-effort: any error → log + report strategy
  downgrade, never block startup.

**Tests:** unit-test the request/response token plumbing pure parts
(token generation, shortcut-id mapping `Action ↔ slug` round-trip).
Live portal calls exercised manually (GNOME session) — documented in
the commit message body? No — documented in `docs/wayland.md` update
(T.3).

**Acceptance:** on GNOME Wayland, first run pops the system shortcut
dialog; accepting delivers `Activated` events into the channel
(observable at debug log level).

## T.2 — Event wiring + fallback chain (M)

**Goal:** portal events drive the same `AnimaEvent`s as X11 hotkeys;
strategy selection becomes runtime behavior.

- Map portal shortcut id → `Action` → `AnimaEvent` (reuse the
  existing `hotkeys::register` mapping table; factor it so both
  backends share one source of truth).
- Winit path: portal thread posts via `EventLoopProxy` (cheap
  handlers — same invariant as the D-Bus service, documented).
  Wayland-native path: drain the bounded channel in the run loop next
  to the D-Bus receiver.
- Strategy: `auto` (default) = portal if probe succeeded, else
  XGrabKey if X11, else none + warning banner. Config override
  `global.hotkey_backend = "auto" | "portal" | "x11" | "none"`
  (serde default `auto`; unknown values → auto + warn).
- The `Warning::GlobalHotkeysUnavailable` banner only fires when the
  *resolved* strategy is none — GNOME Wayland users stop seeing it.

**Tests:** strategy resolution table including overrides; action
mapping round-trip; banner-condition unit test.

**Acceptance:** `Ctrl+Shift+A` toggles edit mode on stock Ubuntu
GNOME Wayland with the app running natively (no XWayland), after
approving the portal dialog once.

## T.5 — Multi-window architecture decision record (S)

**Goal:** decide once, in writing, before touching the renderer.

- `docs/architecture.md` new section: one shared `wgpu::Instance` +
  `Device`/`Queue`; per-window `Surface` + `SurfaceConfiguration`;
  shared texture cache (entity textures are window-agnostic); one
  egui context on the *primary* window only; `WindowId →
  MonitorBinding` registry owned by `App`.
- Why shared device: textures uploaded once for entities visible on
  several monitors (Span), single device-loss domain, egui renderer
  needs one device.
- Pacing generalisation: `redraw_pacing` computes per-window
  deadlines (an entity animates only the window of the monitor it
  sits on); `request_redraw` fans out to affected windows only.

**Acceptance:** the doc; no code.

## T.6 — Window-per-monitor spawn, X11 path (L)

- `MonitorMode::PerMonitor` → one overlay window per
  `MonitorInfo`, positioned/sized to its monitor; `Span` → today's
  single window (default, unchanged); `Single{name}` → one window on
  the named monitor.
- Per-window `X11InputManager` (XShape input region each).
- Window registry: `HashMap<WindowId, WindowSlot>` where `WindowSlot
  { window, renderer_surface, monitor: MonitorInfo, x11_input }`.
- `resumed` spawns per current mode; mode switch at runtime
  (Appearance tab) rebuilds the registry (despawn + spawn, entities
  keep absolute positions; per-monitor windows translate global
  coords → window-local at render).

**Tests:** registry diff logic (mode × monitor set → expected
spawn/despawn list) as pure functions; coordinate translation
round-trip.

**Acceptance:** two monitors + PerMonitor = two overlays, entities
render on the monitor their position resolves to; toggling modes
live doesn't leak windows (registry len matches mode).

## T.7 — Renderer multi-surface support (L)

- Split `WgpuRenderer` into `GpuShared { instance, device, queue,
  pipeline, layouts, textures }` and `SurfaceState { surface, config,
  dynamic_vertex_buffer, dims }`.
- `render(shared, surface_state, draw_list)` per window; draw list
  built per window from entities resolved to that monitor
  (`Span`: all windows get the full list with translated coords —
  v0.6 keeps Span single-window so this stays theoretical).
- egui pass only on the primary surface.
- `prune_stale_textures` runs once per frame on shared cache (not
  per window).

**Tests:** existing renderer tests keep passing (Span path
unchanged); draw-list partition function unit-tested.

**Acceptance:** PerMonitor renders correct subsets; no texture
re-upload when an entity's monitor changes (shared cache hit).

## T.8 — Input routing + edit-mode scoping (M)

- `window_event` dispatches by `WindowId` through the registry;
  cursor/click coordinates translate window-local → global before
  hit-testing.
- Edit mode is global (all windows get full input shape; all show
  the edit bar); panel + palette on primary; ⚙ toggle button on
  every window.
- Selection: clicking an entity in any window selects it; nudges/
  deletes work regardless of which window has focus.

**Tests:** coordinate translation; per-window shape decisions
(mode × window → expected region) pure-function table.

**Acceptance:** drag an entity on monitor 2 while the panel sits on
monitor 1; keyboard nudges apply to the selection wherever it lives.

## T.9 — Monitor hotplug (M)

- winit `Event::NewEvents` + monitor enumeration diff each
  `Resumed`/scale-change; on change: registry diff → spawn/despawn,
  re-run `resolve_monitor_for_position` for pinned entities, toast
  ("Monitor HDMI-A-1 disconnected — 3 entities moved").
- Entities pinned to a vanished monitor fall back to `Auto`
  (existing `monitor-pin-cleared-toast` flow).
- Wayland native: `wl_output` add/remove handlers already exist —
  apply the same diff to layer surfaces (one layer surface per
  output in PerMonitor; Span unchanged).

**Tests:** diff logic against synthetic monitor-set transitions
(add, remove, replace, resolution change).

**Acceptance:** unplug/replug during a session relocates entities
with toasts, no crash, no stale window.

## Risks & mitigations

| Risk | Mitigation |
|------|-----------|
| Portal backend divergence (GNOME one-shot dialog vs KDE editor UI) | Strategy code treats portal replies as authoritative; T.4 renders whatever came back; manual test matrix: GNOME 48+, Plasma 6, sway+xdg-d-p-wlr (no GlobalShortcuts → fallback path). |
| Dev machine can't exercise the portal arm (T.0 finding: Ubuntu 24.04 ships xdg-desktop-portal-gnome 46, GlobalShortcuts landed in 48) | Portal logic stays behind exhaustively unit-tested pure functions; live validation on a Plasma 6 VM or Ubuntu 25.04 live session before T.11; the dev machine validates the X11Grab fallback arm continuously. |
| Multi-window destabilises the default path | `Span` stays the default and keeps the literal current single-window code path; PerMonitor is opt-in until 0.7. |
| Renderer split regresses single-window perf | The split is structural, not behavioral — same call sequence for one surface; perf overlay before/after comparison in T.7 commit. |
| winit multi-window quirks on X11 (focus, stacking) | Each window carries the same EWMH hints as today's single one; known-issues section in wayland.md if Mutter misbehaves. |

# v1.2 — Scripted behaviors

**Status: all six sub-phases landed.**
Two things were decided differently from this document once the code
existed, and the reasons are recorded where they apply below: the script
is top-level statements rather than `fn tick(e)`, and `params` is a map of
numbers rather than a free-form table. One item is deferred: script
failures surface as a toast, not inline in the Inspector — see sub-phase 5.

Umbrella:
[ROADMAP.md](../../ROADMAP.md). Standard gate before each commit
(`cargo fmt --all` + clippy `-D warnings` + `cargo test`).

Theme: per-character motion written as a small script instead of picking
one of five hardcoded `Behavior` variants.

## Why this before system-load behaviors

Both were endorsed post-1.0. Scripting comes first because system-load
reactivity collapses into *one exposed variable* once scripts exist —
`cpu`, `mem` in the script context — instead of a sixth `Behavior`
variant with its own UI, serde defaults and sliders. Built the other way
round, the load work gets rewritten.

## Current state (what we build on)

The extension point is already clean, which is most of why this is
tractable:

- `Behavior` (`src/behavior.rs`, 915 lines) is an internally-tagged serde
  enum: `#[serde(tag = "type", rename_all = "snake_case")]`. A new
  `type = "script"` variant is **purely additive**, so it satisfies the
  1.x config guarantee in [stability-policy.md](../stability-policy.md)
  without a migration.
- `Behavior::tick(&self, state, x, y, ctx)` is the single evaluation
  entry point, called per entity per frame from `entity.rs:192`.
- `TickContext` already carries exactly what a script wants: sprite size,
  `DesktopBounds`, cursor, `dt`, `reduced_motion`.
- `BehaviorState` holds per-entity runtime accumulators alongside the
  serialized config.
- `CONTRIBUTING.md` §"Adding a new behavior" documents the five-step
  recipe; steps 1–5 apply here unchanged.

Two constraints follow from where `tick` runs, and they shape everything
below: it is **on the UI thread**, and it runs **once per entity per
frame**. A script that loops forever freezes the overlay; a script that
is merely slow drops frames on every character.

## Engine: Rhai

**Recommendation: Rhai, not Lua.** Both were considered; the deciding
factors are this project's own invariants, not raw speed.

- **Pure Rust.** No C toolchain. The Windows port is unfinished and the
  BSD/macOS work is queued — adding a C dependency taxes every one of
  them. This project already made `openh264` optional for exactly this
  reason.
- **Deny by default.** Rhai has no file, network or process access
  unless the host registers it. `CONTRIBUTING.md:131` and
  [threat-model.md](../threat-model.md) §"No network" make zero outbound
  connections a hard invariant; with Rhai that stays enforced by the
  engine rather than by review discipline. Lua's `io`/`os`/`package` are
  present by default and must be removed — the failure mode is a subtle
  omission, and it is the wrong default for a hard invariant.
- **Bounded execution.** `set_max_operations`, `set_max_call_levels`,
  `set_max_expr_depths` and `on_progress` give a hard ceiling per tick.
  On the UI thread this is not optional.

Lua is faster, and more familiar to people who have modded other mascot
apps. Neither outweighs the above for a workload of a few arithmetic
operations per entity per frame.

## Shape

### Config

```toml
[characters.behavior]
type = "script"
path = "behaviors/lazy_wander.rhai"

[characters.behavior.params]
speed = 40.0
```

`path` resolves **through the existing containment helper**,
`drop_validate::resolve_library_asset` — canonicalize both sides, reject
anything not under the library root. Scripts get no separate path logic;
the traversal question is already solved and should not be re-answered.

`params` is a free-form table exposed to the script, so a script author
can offer tunables without the app knowing their names.

### Script contract

```rhai
// Called once per frame. Mutate x/y; everything else is read-only.
fn tick(e) {
    e.x += params.speed * e.dt;
    if e.x > e.bounds_max_x - e.w { e.x = e.bounds_min_x; }
}
```

Exposed read-only: `dt`, `w`, `h`, `bounds_min_x/min_y/max_x/max_y`,
`cursor_x`, `cursor_y`, `has_cursor`, `reduced_motion`, `t` (seconds
since the behavior started). Writable: `x`, `y` — matching exactly what
`tick` is allowed to mutate today. Persistent per-entity scratch space
lives in a `state` map, stored in a new `BehaviorState` field.

Keeping v1 to position-only is deliberate: it is the whole of the current
`tick` contract, so nothing else in the engine has to learn about
scripts.

### Failure handling

A script that fails to compile, exceeds its operation budget, or throws
must not take the overlay with it:

- the entity falls back to `Behavior::Idle`,
- **one** toast and **one** log line, not one per frame — the existing
  toast system is there, and a per-frame error would be its own denial of
  service,
- the failure is sticky until the script file changes, so a broken script
  doesn't retry sixty times a second.

### Performance

Non-negotiables, given the UI thread:

- one shared `Engine` for the process (construction is not cheap),
- compile to AST once, cached by path + mtime, never per frame,
- a reused `Scope` per entity,
- `set_max_operations` at a few thousand — enough for real behaviors,
  nowhere near enough to hang a frame.

**Measured** (`cargo bench --bench engine`, `scripted_scene_tick` against
`scene_tick`, same entity counts, one script per entity):

```
 entities   native     scripted    ratio
       10   339 ns      21.8 us     ~64x
       50   1.67 us      110 us     ~66x
      100   3.45 us      230 us     ~67x
```

A script costs roughly **66x** a native behavior, or about **2.3 us per
scripted entity per frame**. The ratio is the alarming-looking number and
the absolute cost is the one that matters: at `MAX_ENTITIES` (64), a scene
where *every* character is scripted spends ~147 us per frame, which is
under 1% of a 60 Hz frame and about 2% of the 8 ms/100-entity budget in
[engine-features.md](../engine-features.md) §7.1.

So this is comfortably affordable, and the interpreter is not worth
optimising until something else in the frame is. What the numbers do
justify is the operation cap: the difference between 2.3 us and a hung
frame is entirely that limit.

The comparison lives in the scheduled benchmark canary, so a regression
in either direction shows up without anyone remembering to look.

## Security posture

Worth stating plainly rather than implying: **a script is code, and this
is a real increase in what a malicious file can do.** Today the worst a
dropped asset can do is exercise the decoders. A script executes.

What contains it:

- Rhai is sandboxed — no fs, no net, no process spawn, and `eval` can be
  disabled outright.
- Scripts must live under the library root, resolved with the same
  canonicalize-and-contain helper as assets.
- Operation limits bound CPU; there is no allocation-heavy surface
  exposed.

What does **not** contain it: nothing stops a script from moving a
character somewhere annoying. That is the feature.

This is the same trust class as the assets a user chooses to install, but
it is not identical, and [threat-model.md](../threat-model.md) should say
so explicitly rather than let "user-chosen content" cover both.

## Sub-phases

One commit each, in order:

1. `Behavior::Script` variant + serde defaults, `tick` arm returning
   `Idle` behaviour. No engine yet — proves the config round-trips and
   that older configs are unaffected.
2. Rhai engine wiring: shared engine, AST cache, scope, limits. Native
   behaviors untouched.
3. The context bridge (read-only fields, writable `x`/`y`, `state` map)
   with unit tests over each exposed field.
4. Failure handling: fallback to Idle, one-shot toast, sticky until the
   file changes.
5. Inspector UI — script picker and `params` editor. **The inline error
   was dropped**: surfacing it there means threading the `ScriptHost`
   through `panels::settings`, which already carries about twenty
   parameters and is called from both backends, for a message the user
   already receives as a toast. Revisit if that call site is ever
   refactored into a struct.
6. Benchmark in the scheduled canary; docs (`CONTRIBUTING.md` recipe
   gains a scripting section, threat-model note, an example script).

## Open questions

- **Hot reload.** Config hot-reload exists; script files are a second
  source that can change independently. Watch mtime, or reload only with
  the config? Watching is friendlier for authoring and is probably worth
  the extra path.
- **Shipping example scripts.** Re-implementing the five native
  behaviors in Rhai would be the best documentation, and would prove the
  API is expressive enough. It also invites "why are there two
  implementations" — they should be examples, not replacements.
- **`params` typing.** Free-form is friendliest to script authors and
  worst for the Inspector, which cannot build sliders for names and
  ranges it does not know. A script may need an optional manifest block
  declaring its tunables.

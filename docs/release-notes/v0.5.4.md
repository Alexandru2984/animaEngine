# animaEngine 0.5.4 — post-refactor audit follow-up

After 0.5.3 closed the second-round audit, the four refactors that
landed against the unreleased tree (`src/app.rs` →
`src/app/`, `src/ui/panels.rs` → `src/ui/panels/`,
`src/keybindings.rs` → `src/keybindings/`,
`src/wayland/layer_window.rs` → `src/wayland/layer_window/`)
brought a third-round audit on the codebase as it stands now. The
refactor itself was clean — every protocol handler / panel /
dispatch arm kept its behaviour. Two HIGH and two MEDIUM items were
caught that had been latent since earlier releases and that the
prior passes missed, plus two LOW items from a manual review. None
of them is exploitable from a cold start; this is incremental
hardening, not a hot patch.

## What's fixed in 0.5.4

### H1 — config_path falls back to a uid-scoped tmpdir

`AppConfig::config_path()` had kept the original `HOME=.` fallback
that the **M3** (0.5.2) pass closed in `perf.rs` and
`asset_library/mod.rs` but missed in `config.rs`. A wrapper script
like `HOME=/etc/cron.d anima-engine` could therefore still
redirect `atomic_write_bytes` on `config.toml` into an
attacker-chosen directory whenever `directories::ProjectDirs`
returned `None` (rare but reachable in minimal containers / broken
envs). Fallback now matches the rest of the codebase:
`std::env::temp_dir().join("animaEngine-<uid>").join("config.toml")`.

### H2 — `MAX_ENTITIES` enforced at every runtime push site

The cap (`MAX_ENTITIES = 64`) was only enforced in
`AppConfig::load()`. Every runtime push path — drag-drop, library
"Add to scene", duplicate, preset Append, context-menu duplicate —
reached `Scene::add_entity_from_path` or
`Scene::append_character_config` directly and bypassed the cap.
A sustained drop-flood from a hostile compositor (up to
`MAX_URI_LIST_PATHS = 256` paths per drop × `MAX_CONCURRENT_DROPS
= 4` workers, plus repetition) could therefore have spawned an
arbitrary number of entities until OOM, even though per-entity
caps (`MAX_DECODED_ASSET_BYTES`) limited each one's memory. Both
functions now gate the push against `MAX_ENTITIES` and return an
error toast when the cap is hit.

### M1 — redaction sweep on three post-refactor info logs

The **M4** (0.5.2) + **G.1** (0.5.3) sweep missed three info-level
traces that newly stood out after the refactor split things apart:

- `scene.rs::add_entity_from_path` — `asset_path_str` (absolute,
  derived from `current_dir().join`)
- `app/lifecycle.rs` — asset library scan summary (`root.display()`)
- `app/render_loop.rs` — perf-snapshot export (`path.display()`)

All three now go through `crate::drop_validate::redact_path` at
`info!`; the full path is downgraded to `debug!`. The
perf-snapshot toast still shows the full path because the user
just requested the export — they want to find the file in their
file manager.

### M2 — `i18n::t()` recovers from poisoned `RwLock`

`i18n::t()` / `set_locale()` used `.expect("i18n state poisoned")`
on the inner `RwLock`. `t()` runs on every frame from every panel,
so a poisoned lock would take the render thread down on the next
translation. Today no writer can poison the lock (only
`set_locale` is a writer and it can't panic mid-write), but the
risk was latent and the inner state is trivially recoverable —
bundles are immutable `Arc`s. Both call sites now recover via
`unwrap_or_else(|poisoned| poisoned.into_inner())`.

### L2 — library log injection via `relative_path`

Library "Add to scene" log lines used `outcome.relative_path`
directly. A hand-edited `library.toml` with RTL-override or
zero-width chars could plant visually reversed strings in
journald. Same threat model as **G.3** but on the log side
instead of egui input. Redacted at `warn!` (filename only),
downgraded to `debug!` for the raw form.

### L3 — `KeyCode::from_str` panic guards made explicit

Two `.unwrap()` calls (`s.chars().next().unwrap()` and
`c.to_digit(10).unwrap()`) had their preconditions enforced by
surrounding `if s.chars().count() == 1` and `'0'..='9'` match-arm
guards. Sound today but a refactoring trap: anyone reordering the
arms or moving the count check would silently turn those into
panic sites for malformed config chord strings. Replaced with
`.expect(…)` strings that name the invariant.

## Upgrade notes

`config.toml` files saved by any prior version decode unchanged.
Observable user-facing changes:

- Drag-drop / library "Add to scene" log lines that newly went
  through `info!` (scene, lifecycle, render-loop) now show the
  file name only. Set `RUST_LOG=anima_engine=debug` to see full
  paths when bug-hunting. The perf-snapshot toast still shows the
  full path on screen.
- Drag-drop / library "Add to scene" / duplicate / preset Append
  refuse to add new entities once 64 are present in the scene.
  Real-world impact: zero unless you were already running with
  more than 64 simultaneous entities, in which case `config.toml`
  was already silently truncated to 64 on load.
- Hand-edited `library.toml` paths with non-printable chars now
  show in `info!` logs as the redacted filename instead of the
  raw bytes. Set `RUST_LOG=anima_engine=debug` to see the raw
  form when bug-hunting.

```bash
# Debian / Ubuntu
sudo apt install ./anima-engine_0.5.4-1_amd64.deb

# AppImage
chmod +x animaEngine-0.5.4-x86_64.AppImage
./animaEngine-0.5.4-x86_64.AppImage
```

## Audit status post-0.5.4

All 0.5.0 audit findings closed (3 critical + 4 high in 0.5.1,
4 medium in 0.5.2). The 0.5.2 re-audit's 2 medium + 4 low findings
closed in 0.5.3. The 0.5.3 post-refactor audit's 2 high + 2 medium
+ 2 low findings closed in this release. One remaining LOW
(`KeyBindings.map` per-action vector cap on deserialize) is
accepted under the same-user threat model — a user who can
hand-edit their own `config.toml` is already past authentication.
The remaining informational items from earlier rounds (TOCTOU
between `pre_validate` and decoder, egui `TextEdit` without focus
restoration) are documented invariants accepted with no action.
